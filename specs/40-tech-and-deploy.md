## Первичная настройка Supabase

1. Создать проект на supabase.com. Регион — ближайший к РФ (Frankfurt).
2. SQL Editor → выполнить [`supabase/schema.sql`](../supabase/schema.sql).
3. SQL Editor → выполнить [`supabase/seed.sql`](../supabase/seed.sql).
   Он заводит **токен организатора** и выводит ссылку на админку — скопировать сразу.
   Докторов seed не создаёт: их заводят в админке по мере того, как находятся.
   Тот же запрос позже покажет и персональные ссылки докторов.
4. Project Settings → API → скопировать `Project URL` и `anon public` ключ
   в [`config.js`](../config.js).

### Про anon key в открытом коде

`anon key` публичен по природе — он лежит в JS любого клиента Supabase.
Безопасность обеспечивается **на стороне БД**, а не сокрытием ключа:

- RLS включён на всех таблицах, политик нет → прямой доступ к таблицам закрыт;
- наружу торчат только `v_doctors` и `v_occupancy` — **без роли и темы вопроса участника**;
- всё, что написал участник, доступно только через RPC, проверяющие токен.

Что может сделать посторонний с `anon key`: записаться на свободный слот
(то же, что и любой участник) и создать бронь на странное время внутри дня мероприятия.
И то и другое видно организатору в админке и удаляется в клик.

### Про токены

Токены — случайные 24 hex-символа в таблице `access_tokens`, недоступной анониму.
Паролей нет: внутреннее мероприятие на три часа, секретная ссылка — адекватный уровень.

Ротация: удалить строку из `access_tokens` и пересохранить карточку доктора в админке —
токен сгенерируется заново.

## Деплой

```bash
git add -A && git commit -m "…" && git push
```

GitHub Pages раскатывает сам за 30–60 секунд. **Сборки нет.**

Первичная настройка репозитория:
1. `gh repo create sdd-doctor/sdd-doctor.github.io --public`, затем запушить `main`
2. Pages включаются сами: у репозитория с именем `<организация>.github.io` источником
   сразу становится ветка `main`, папка `/ (root)`, HTTPS принудительный
3. Файл `.nojekyll` в корне обязателен — иначе Jekyll может съесть служебные пути.

Адрес: `https://sdd-doctor.github.io/`

Сайт живёт в организации `sdd-doctor`, а не в личном аккаунте: имя организации целиком
становится адресом. Ради этого домен и переехал — `https://aserzhantov.github.io/sdd-doctor/`
на слайде и на печатной табличке читался как технический путь.

Своего домена (`sdd-doctor.ru`) сознательно нет: зона `.ru` продаётся минимум на год
и требует паспортных данных, а сертификат на кастомный домен GitHub выпускает
до суток. `*.github.io` покрыт wildcard-сертификатом и работает сразу.

## Что где меняется

| Что | Где | Деплой |
|---|---|---|
| Тексты карточек, стол, вкл/выкл | Админка → БД | Нет |
| Новый доктор | Админка | Нет |
| Удалить бронь | Админка → БД | Нет |
| Длина приёма, окно дня, дата | `config.js` | Да |
| Цвета и метрика | Токены в `:root` в `assets/styles.css` | Да |

**Карточка доктора целиком живёт в БД.** Фотографий в проекте нет — изображение лица это
персональные данные, см. [60-backlog.md](60-backlog.md). Поэтому нового доктора можно завести
прямо на площадке, без деплоя.

**Смену `SLOT_MINUTES` делать до открытия записи.** Брони хранят абсолютное время;
при смене сетки они станут `off-grid` — показываются отдельной строкой и у участника,
и у доктора, не пропадают, но занять их нельзя.

При переносе даты править `CONFIG.DAY` **и** констрейнт `bookings_event_day`
в `schema.sql` — иначе брони перестанут создаваться.

## QR-код

Код **один** — и для показа со сцены, и для табличек на столах. Ведёт на витрину докторов.
Почему не сделали отдельный QR на каждый стол — см. [10-flows.md](10-flows.md), раздел «QR: почему он один».

```bash
qrencode -o qr/main.png -s 20 -m 4 -l M "https://sdd-doctor.github.io/"
zbarimg -q --raw qr/main.png      # проверка, что код читается обратно
```

Уровень коррекции `M` и `-s 20` проверены на прошлом мероприятии: код читается
с экрана зала и с печатной таблички.

## Таблички на столы

`card.html?t=<admin_token>` собирает печатные таблички по всем активным докторам.

Три зоны слева направо: **номер стола** отдельной панелью, **доктор** — алиас, роль,
специализация и описание опыта, **QR** на запись. Двухколоночный вариант
оставлял пустоту в середине листа, поэтому центр отдан под опыт.

Фотографии в блоке доктора нет, и освободившиеся 30 мм отданы алиасу: он набран 12 мм
и остался единственным, чем доктор представлен на листе.

Тексты ограничены по числу строк (алиас и роль — 2, специализация — 2):
макет не должен разъезжаться от того, что напишут в админке. Длинное описание
обрезается многоточием, подвал с правилом приёма остаётся на листе.

Опыт — исключение: его предел считается на месте, после загрузки шрифтов. В CSS
стоит 8 строк — столько влезает в худшем случае, когда алиас, роль и чип разошлись
каждый на две строки; `fitBio()` в `card.html` меряет фактический остаток колонки
и поднимает предел до него. Когда алиас в одну строку, это 10–11 строк вместо 8,
и низ колонки занят текстом, а не белым полем.

- Формат **A4 альбомная** (297×210 мм), по одной табличке на страницу.
- В диалоге печати: поля «Нет», **включить «Фоновая графика»** (иначе пропадут
  фирменная полоса и подложка чипа; сам номер стола напечатается в любом случае —
  он сделан сплошным цветом специально ради этого).
- Печатать на плотной бумаге, сгибать домиком или ставить в держатель.

Табличка отвечает за навигацию по залу, а выбор доктора происходит на витрине.
Поэтому при замене доктора достаточно перепечатать одну табличку — ссылка не меняется.

## Чек-лист дня мероприятия

**За неделю**
- [ ] Завести докторов в админке: алиас, роль, специализация, описание, номер стола
- [ ] Собрать у докторов алиасы и описания опыта
- [ ] Разослать докторам их персональные ссылки на `doctor.html`
- [ ] Зафиксировать `SLOT_MINUTES` и окно дня — после этого не менять

**За день**
- [ ] **Открыть лендинг с личного телефона по мобильному интернету на площадке.**
      Проверить и `github.io`, и что запись реально проходит. Это единственная проверка,
      которую нельзя сделать за столом заранее
- [ ] Напечатать таблички на столы из `card.html` — по одной на каждого доктора
- [ ] Подготовить общий QR для показа со сцены (`qr/main.png`)
- [ ] Выгрузить CSV записей и распечатать — офлайн-страховка, если сеть ляжет

**В день**
- [ ] Показать QR со сцены на открытии и проговорить: **приём только по записи**
- [ ] Ошибочные брони удаляются организатором в админке

**Если сеть легла**
- Лендинг остаётся живым: показывает докторов из кэша, правила и столы,
  честно пишет, что запись недоступна.
- Работаем по распечатанному CSV: дежурный сверяет по списку.

## Локальная проверка

```bash
python3 serve.py   # из корня проекта
```

Открыть `http://localhost:8766/`. Работает без сборки, файлы правятся на лету.
Свой сервер, а не `python3 -m http.server`: встроенный кеширует, и правки
в `app.js` и `styles.css` молча не применяются.

Полный список проверок — в конце плана реализации; ключевые:
- две вкладки жмут один слот одновременно → ровно одна бронь, второй видит понятную ошибку;
- `curl` по `anon key` к `v_occupancy` не возвращает роли и темы вопроса;
- отключить сеть → страница живая, запись честно сообщает о недоступности;
- ширина 360px, время по МСК корректно при любой таймзоне устройства.
