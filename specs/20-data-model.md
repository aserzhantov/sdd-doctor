# 20 — Модель данных и контракты API

Хранилище — **Supabase** (Postgres + PostgREST). Клиент ходит только через `anon key`.

Реализация: [`supabase/schema.sql`](../supabase/schema.sql) (структура, идемпотентно),
[`supabase/seed.sql`](../supabase/seed.sql) (стартовые доктора).

---

## Принцип разделения

**В БД лежит только то, что меняется людьми во время жизни проекта:** тексты карточек и брони.
Тайминг, фото, дизайн и логика лежат в git — см. [40-tech-and-deploy.md](40-tech-and-deploy.md).

**Слоты в БД не хранятся.** Сетка вычисляется на клиенте из `config.js` и окна доктора.
БД знает только про занятость конкретных моментов времени.

---

## Грабли Supabase: схема `extensions`

В Supabase расширения ставятся **не в `public`, а в схему `extensions`**. Поэтому:

- у всех `security definer` функций `search_path = public, extensions`;
- вызовы `gen_random_bytes` квалифицированы явно.

Без этого функция падает с `42883 function gen_random_bytes(integer) does not exist`,
причём **только внутри функций**: тело plpgsql разбирается в момент выполнения,
с её собственным `search_path`. Прямой SQL в редакторе при этом работает,
поэтому ошибка не видна ни локально, ни при прогоне `seed.sql` — она вылезает
только на первом реальном вызове RPC.

## Таблицы

### `doctors`

| Поле | Тип | Примечание |
|---|---|---|
| `id` | `text` PK | латиница, напр. `ivanov`. **Он же имя файла фото** |
| `name` | `text` NOT NULL | |
| `role` | `text` | должность и команда |
| `specialty` | `text` | с чем помогает |
| `bio` | `text` | 2–4 предложения про опыт |
| `table_no` | `int` | номер стола в зоне |
| `win_start`, `win_end` | `time` | личное окно; `NULL` → окно дня из `config.js` |
| `sort` | `int` | порядок в витрине |
| `active` | `boolean` | выключить, не удаляя данные |

`id` неизменяем после создания: он завязан на имя файла фотографии.

### `bookings`

| Поле | Тип | Примечание |
|---|---|---|
| `id` | `uuid` PK | |
| `doctor_id` | `text` FK → `doctors` | `on delete cascade` |
| `slot_start` | `timestamptz` NOT NULL | абсолютный момент начала приёма |
| `kind` | `text` | `participant` \| `blocked` |
| `name`, `team` | `text` | заполнены только у `participant` |
| `cancel_code` | `text` | генерится сам, отдаётся только тому, кто записался |
| `created_at` | `timestamptz` | |

**`unique (doctor_id, slot_start)` — главная защита целостности.** QR показывают со сцены,
сотня человек открывает страницу одновременно. Индекс физически исключает двойную запись:
второй получает ошибку `23505`, а не «слот занят, но записали обоих».

**`check` на дату мероприятия — серверная защита.** Тайминг лежит в клиентском файле, поэтому
сервер не знает окно дня и не может валидировать слот полностью. Констрейнт отсекает брони
на произвольную дату от того, у кого есть `anon key`. Остаточный риск — бронь на 03:00 того же
дня; видна в админке и удаляется в клик. Для внутреннего трёхчасового мероприятия это адекватно.

> При переносе даты мероприятия констрейнт `bookings_event_day` надо править вместе с `CONFIG.DAY`.

### `access_tokens`

| Поле | Тип | Примечание |
|---|---|---|
| `token` | `text` PK | случайные 24 hex-символа |
| `role` | `text` | `doctor` \| `admin` |
| `doctor_id` | `text` FK | заполнен только для роли `doctor` |
| `label` | `text` | для чего выдан |

Паролей нет. Секретная ссылка — адекватный уровень для внутреннего мероприятия на три часа.
Таблица недоступна анониму ни в каком виде.

## Доступ: что видно наружу

RLS включён на всех трёх таблицах, политик нет → прямой доступ для `anon` закрыт полностью.
Наружу торчат только две view и набор RPC.

**Правило, которое нельзя нарушать: имена и команды сотрудников не должны быть доступны
по `anon key`.** Публичная витрина отдаёт занятость без ПДн.

| Объект | Отдаёт | Кто может |
|---|---|---|
| `v_doctors` | карточки активных докторов | аноним |
| `v_occupancy` | `doctor_id, slot_start, kind` — **без имён** | аноним |

## RPC

Все функции `security definer` с фиксированным `search_path`.

### Публичные

#### `book_slot(p_doctor_id, p_slot_start, p_name, p_team) → json`

Возвращает `{"id": "<uuid>", "cancel_code": "<hex>"}`.

Серверно проверяет: доктор существует, `active = true`, длина имени 2–60, команды 2–80,
слот попадает в личное окно доктора, если оно задано. Клиентская валидация защитой не считается.

| Код ошибки | Значение | Что показать |
|---|---|---|
| `23505` | слот уже занят | «Этот слот только что заняли» + перезагрузить занятость |
| `P0002` | доктора нет | «Доктор больше не принимает» |
| `P0003` | доктор выключен | «Доктор больше не принимает» |
| `P0004` | имя или команда не прошли валидацию | подсветить поле |
| `P0005` | слот вне окна доктора | «Это время недоступно» |
| `23514` | дата вне дня мероприятия | «Это время недоступно» |

#### `cancel_booking(p_id, p_code) → boolean`

Удаляет бронь, только если совпал `cancel_code` и `kind = 'participant'`.
`false` означает, что брони уже нет — клиент чистит `localStorage` и сообщает,
что запись могли отменить организаторы.

### Под токеном доктора

- `doctor_bookings(p_doctor_id, p_token)` → `id, slot_start, kind, name, team`
- `doctor_block_slot(p_doctor_id, p_slot_start, p_token, p_blocked)` → `boolean`
  Блокировка = вставка строки с `kind='blocked'`. Занятый участником слот заблокировать нельзя:
  сработает тот же уникальный индекс (`23505`).

### Под токеном админа

- `admin_list_doctors(p_token)` — **все** доктора, включая выключенных, вместе с их токенами
  (нужно для кнопки «Ссылка для доктора»)
- `admin_upsert_doctor(p_token, p_id, p_name, p_role, p_specialty, p_bio, p_table_no, p_win_start, p_win_end, p_sort, p_active)`
  Создание и правка — одна функция. При создании нового доктора автоматически заводит ему токен доступа.
- `admin_all_bookings(p_token)` — все брони с именами и названиями докторов, для таблицы и экспорта CSV
- `admin_delete_booking(p_token, p_id)` → `boolean`

Ошибка доступа во всех токенных функциях — `P0001` (`FORBIDDEN`). Клиент показывает
«Ссылка недействительна» и не грузит ничего.

## Правила слотов на клиенте

```
начало = doctor.win_start ?? CONFIG.WINDOW.start
конец  = doctor.win_end   ?? CONFIG.WINDOW.end
слоты  = [начало, начало + SLOT, …] пока slot_end <= конец
```

Каждый слот — абсолютный момент на дату `CONFIG.DAY` в МСК. Занятость матчится по точному
совпадению `slot_start`.

**`off-grid`:** бронь, чей `slot_start` не совпал ни с одним слотом сетки. Возникает, только если
`SLOT_MINUTES` или окно поменяли после появления броней. Рендерится отдельной строкой под сеткой —
чтобы бронь не пропала молча. Занять её нельзя.

## Как заводятся доктора

Два пути, оба ведут в одну и ту же `admin_upsert_doctor`:

1. **`supabase/seed.sql`** — первичное заполнение всех разом, запускается в SQL-редакторе Supabase.
   Лежит в git → воспроизводимо: снёс проект или поднимаешь второй стенд, восстановил одним запуском.
2. **Форма в админке** — пустая = создание, заполненная = правка.

Практически: до мероприятия заводишь всех через `seed.sql`, дальше правишь тексты в админке
по мере того, как доктора присылают описания.
